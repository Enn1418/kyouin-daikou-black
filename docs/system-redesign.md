## 1. 全体の階層

```
第1階層  CEO（利用者）
          依頼・全体方針の決定・重要な判断・最終承認
             │
第2階層  秘書室
          CEOの補佐。要件の確定・タスク分解・割り当て・進捗管理・調整・取りまとめ
             │
制御層   ワークフロー制御（決定的なコード。LLMではない）
          処理順序・並列・条件分岐・状態遷移・承認待ち・差し戻し・エラー処理・呼び出し
             │
第3階層  専門部門
          図書館 / 書庫 / 単元設計室 / 特別支援サポーター / 板書室 / 視覚教材室 /
          同時異教材室 / 国語教材室 / 算数教材室 / 自立活動室 / 広報室
             │
独立監査  品質管理室
          制作部門から独立。合否を判定し、差し戻し先を指定する。自分の判定を自分で承認しない
```

### 1.1 表示名の変更

`USER_NAME` と画面上の「担任」表記を **CEO** に変える。

ただし**プロンプトの中では「CEO（担任）」と書く**ことを推奨する。
エージェントに対して「担任」という語は教育上の役割（学級を持ち、児童の実態を知っている人）を
伝える情報を含んでおり、CEO だけにすると教材の書きぶりが企業向けに寄る恐れがある。
画面表示は CEO、プロンプト内部は「CEO（担任）」。ここは CEO の指示があれば全面変更する。

### 1.2 三者の責任範囲（重複させない）

| | 決めること | 決めないこと |
|---|---|---|
| **CEO** | やるかどうか、方針、承認、中止 | 誰にどの順で割り振るか |
| **秘書室** | 何を作るか、誰に頼むか、どうまとめるか | 実際にいつ動かすか（制御層の仕事） |
| **制御層** | いつ動かすか、次はどこか、止めるか戻すか | 中身の良し悪し（品質管理室の仕事） |

**秘書室は「計画を書く」。制御層は「計画を実行する」。** 秘書室が直接エージェントを起動しない。
これを分けないと、LLM が工程を飛ばしたり、品質管理を通さず完了にしたりする事故が必ず起きる。

## 2. 案件と依頼票（要件定義）

### 2.1 データの形

```ts
/** 依頼1件。すべての部門がこれを見る。 */
interface Job {
  id: string;
  title: string;
  status: JobStatus;
  sheet: RequirementSheet;      // 依頼票（確定した条件）
  unit?: UnitAnalysis;          // 単元分析（単元設計室の成果）
  plan?: WorkPlan;              // 段取り（秘書室の成果）
  proposalHtml?: string;        // 単元構成案（HTML）
  blueprintHtml?: string;       // システム設計図（HTML）
  approvals: Approval[];
  deliverables: Deliverable[];
  qaReports: QaReport[];
  events: JobEvent[];           // 監査用。誰が何をいつ
  createdAt: string; updatedAt: string;
}

/** 依頼票。★ は必須。埋まるまで制作に進めない（制御層が止める）。 */
interface RequirementSheet {
  subject: string;          // ★ 教科
  grade: string;            // ★ 学年（複数学年可。特支は「1〜4年」等）
  unitName: string;         // ★ 単元名
  teachingContent: string;  // ★ 指導したい内容
  competencies: string;     // ★ 児童に身につけさせたい力
  hours: number;            // ★ 授業時数
  pupils: string;           // ★ 児童の実態（匿名IDのみ。既定は 00_共通/学級の実態.md）
  participants: string[];   // ★ この単元に参加する児童（匿名ID）
  ict: string[];            //   使用できるICT機器・教材
  wantedOutputs: string[];  // ★ 希望する成果物（指導案／略案／教材／掲示物／板書／おたより…）
  outputFormats: OutputFormat[]; // ★ 出力形式（Markdown / 印刷用HTML / 画像 / 一式）
  style: string;            //   出力スタイル（詳しい指導案 / 略案 / 児童用のみ 等）
  constraints: string;      //   その他の制約・希望（時間がない、この教具は使えない 等）
  dueDate?: string;
}

type OutputFormat = 'md' | 'print-html' | 'image' | 'bundle';
```

### 2.2 不足項目の確認（要件2）

制御層が `sheet` の★項目を機械的に検査する。**LLM の判断に任せない**（聞き忘れが起きるため）。

1. 空の★項目があれば `status = '要件確認'` にする
2. 秘書室の**要件ヒアリング担当**が、空の項目だけを、まとめて1回の質問文にする
   （1項目ずつ聞くのは CEO の負担。「不足は3つです」と並べて出す）
3. 書庫に過去の似た案件があれば、**既定値の候補**として添える
   （例:「前回の算数は45分×6時間・印刷用HTMLでした。同じでよいですか」）
4. CEO が答えると `sheet` が確定し、`sheetLockedAt` が入る
5. **確定後の依頼票は、全部門のプロンプト冒頭に同一の文面で差し込まれる。**
   途中で方針がぶれないのは、全員が同じ1つの文字列を見ているため

### 2.3 依頼票の共有方法

`PromptBuilder` に S14 を追加し、`teamType === '特別支援'` の全部門の
システムプロンプト先頭に、確定した依頼票の要約（600字以内）を差し込む。

```
【この案件の条件（確定済み・変更不可）】
教科: 算数 ／ 学年: 1〜4年 ／ 単元: かさ（LとdL） ／ 時数: 6
参加児童: A児・B児・D児
身につけさせたい力: …
使えるICT: 大型提示装置・タブレット（1人1台）
希望する成果物: 指導案（略案）・3段階のプリント・板書計画・絵カード
出力形式: 印刷用HTML ／ 制約: 45分・裏面なし
条件が実態と合わない場合は、勝手に変えず秘書室に申し出ること。
詳細: 04_案件/かさ_2026-09/依頼票.md
```

## 3. ワークフロー制御層

### 3.1 なぜコードで書くか

**制御層は決定的な TypeScript にする。LLM に司会をさせない。**

理由: LLM に順序管理をさせると、確率的に工程を飛ばす。品質管理を通さず完了にする、
差し戻しを無限に繰り返す、同じ部屋を二重に起動する——これらは「たまに起きる」ので
テストで捕まえにくく、CEO が気づいたときには成果物が出てしまっている。
このリポジトリはすでに、ドリルの数値・図・板書の寸法を決定的なコードに寄せる方針で作られている。
**司会も同じ理由でコードに寄せる。**

配置: `src/core/workflow/WorkflowEngine.ts`（新規）。`RoomManager` の上、UI の下。

### 3.2 案件の状態

```
受付 → 要件確認 ⇄(質問) → 調査 → 単元分析 → 構成案作成
     → 【承認待ち①】─ 実行 ─→ 制作 → 品質管理 ⇄ 修正 → 統合 → 【承認待ち②】→ 完了
          │  └ 修正 → 構成案作成 に戻る
          └ 中止 → 中止
```

| 状態 | 開始条件 | 完了条件 | 担当 |
|---|---|---|---|
| 受付 | CEO が依頼を出した | 依頼票の器ができた | 秘書室 |
| 要件確認 | ★に空がある | ★がすべて埋まった | 秘書室（ヒアリング） |
| 調査 | 依頼票が確定 | 図書館・書庫の両方が返した | 図書館・書庫（**並列**） |
| 単元分析 | 調査が完了 | 単元目標・評価規準・学習過程が揃った | 単元設計室 |
| 構成案作成 | 単元分析が完了 | 構成案HTML＋設計図HTML が生成された | 秘書室 |
| **承認待ち①** | 上記2点が揃った | CEO が 実行／修正／中止 を選んだ | **CEO** |
| 制作 | 実行が選ばれた | 全 step が done | 各専門部門（**並列**） |
| 品質管理 | step が成果物を出した | 合否が出た | 品質管理室 |
| 修正 | 品質管理が不合格 | 差し戻し先が再提出した | 元の部門 |
| 統合 | 全 step 合格 | 1つの成果物一式になった | 秘書室（統合担当） |
| **承認待ち②** | 統合完了 | CEO が承認 | **CEO** |

### 3.3 段取り（WorkPlan）

```ts
interface WorkPlan { steps: PlanStep[]; }

interface PlanStep {
  id: string;
  roomId: string;              // どの部門が
  title: string;               // 何を（例:「3時間目の板書」）
  brief: string;               // 依頼文（依頼票は別途自動で入る）
  dependsOn: string[];         // 先に終わっているべき step
  parallelGroup: number;       // 同じ番号は同時に動かせる
  startCondition: string;      // 人間が読める開始条件
  doneCondition: string;       // 人間が読める完了条件（＝品質管理の合格基準）
  qaProfile: QaProfile;        // どの観点で検査するか
  status: 'pending'|'ready'|'running'|'qa'|'rework'|'done'|'skipped'|'error';
  reworkCount: number;
  assignedAt?: string; doneAt?: string;
}
```

段取りは**秘書室のタスク設計担当が作る**が、機械可読な形（上記）で出す。
制御層はこれを読んで動かすだけで、内容の解釈はしない。

### 3.4 制御の中身（毎回の処理）

```
tick(job):
  1. dependsOn が全部 done の pending → ready
  2. ready のうち、その部屋が空いている step → running
       roomManager.ensure(roomId) → startProject(brief, roomId)
       部屋が埋まっていれば待機（同じ部屋の二重起動を防ぐ）
  3. running の step が deliver_project を出した → qa
  4. qa の判定:
       合格   → done
       不合格 → rework（差し戻し先＝品質管理室が指定した部門）、reworkCount++
  5. reworkCount > 2 → CEO へエスカレーション（承認待ちに落とす）
       「3回直しても基準に届きません。基準を下げるか、方針を変えるか」
  6. error（APIエラー・情報不足）→ §3.5
  7. 全 step done → 統合 → 承認待ち②
```

### 3.5 エラーと情報不足の扱い

| 事象 | 対応 |
|---|---|
| APIの一時的な失敗 | 2回まで自動で再試行（間隔を空ける）。3回目で error |
| 情報不足を部門が申告 | その step を `blocked` にし、質問を秘書室へ。**他の step は止めない** |
| 出典が見つからない（図書館） | 「見つかりませんでした」を成果として返す。捏造させない。単元分析は「要確認」付きで進む |
| ブリッジ未接続 | 図書館の外部資料と書庫が使えない → **縮退運転**（§9）。制作は続く |
| 画像生成が使えない | 代替経路（§6.3）。ワークフローは止めない |
| 差し戻し3回超 | CEO にエスカレーション |
| 部屋が埋まっている | 待機。取りこぼさない |

### 3.6 最終成果物を出す条件

次を**すべて**満たしたときだけ出力する。

1. `plan.steps` のうち `skipped` 以外がすべて `done`
2. すべての `done` に、品質管理室の**合格**記録がある
3. 依頼票の `wantedOutputs` が全部そろっている（秘書室が突き合わせ）
4. 未確定事項が残っていれば、成果物の冒頭に一覧で明記されている
5. CEO が承認待ち②で承認した

#### 独立性をどう担保するか

1. **別の部屋にする。** 品質管理室は制作部門と別の `AgentSimulation` を持ち、
   会話履歴を共有しない。作った本人が自分を検査する構造にならない
2. **判定は品質管理室、進路は制御層。** 品質管理室は合否と差し戻し先を出すだけで、
   自分で「完了」にはできない。状態を進めるのは制御層
3. **不合格の記録が残る。** `QaReport` は `job.qaReports` に積まれ、CEO がいつでも見られる。
   合格に上書きされない
4. **再検査は必須。** 差し戻して直したものは、必ずもう一度品質管理室を通る

```ts
interface QaReport {
  id: string; jobId: string; stepId: string;
  verdict: '合格' | '不合格';
  checks: { item: QaItem; ok: boolean; note: string }[];
  reason: string;              // 不合格の理由
  sendBackTo?: string;         // 差し戻し先の roomId
  checkedAt: string;
}
```

## 5. 承認を挟む制作フロー

### 5.1 承認待ち①で出す2つの書類

**① 単元構成案**（要件12・追加3①）— 依頼内容と目的／対象学年と教科／単元名／単元の価値／
学習指導要領との関連／育成を目指す資質・能力／単元目標／評価規準／児童の実態／予想されるつまずき／
必要な支援／単元全体の学習過程／各時間の概要／使用する教材とICT／制作予定の成果物／
参照資料と出典／未確定事項。

**② システム設計図**（追加3②）— 今回の CEO／秘書室／使う部門とエージェント／各エージェントの役割／
各工程の入力と出力／情報の流れ／処理順序／並列工程／図書館・書庫から取る情報／
品質管理のタイミング／承認地点／差し戻し先／完成までの流れ。

どちらも **HTML** で出す（`bridge/markdown.mjs` ＋ 新しいテンプレート）。
設計図は階層図・工程表・担当・参照資料・品質確認結果を含む。
ブリッジ未接続のときはアプリ内に表示する。

### 5.2 停止と選択

構成案と設計図を出した時点で `status = '承認待ち①'` にし、**制御層が完全に停止する**。
CEO の選択肢は3つ。

| 選択 | 起きること |
|---|---|
| **実行** | `制作` へ進む。ここで初めて指導案・教材・掲示物を作り始める |
| **修正** | 指示を反映して `構成案作成` に戻り、再提示。承認待ち①に戻る |
| **中止** | `中止`。作りかけは残すが成果物は出さない |

**CEO が「実行」を選ぶまで、最終成果物は1つも作らない。** これは制御層の状態機械で保証する
（LLM の自制に頼らない）。

## 6. 画像生成の扱い

### 6.1 現状

`GeminiProvider.generateImage` は**すでに実装され動いている**（`@google/genai`、
`gemini-3.1-flash-image-preview` 既定、1K〜4K、価格表も実装済み）。
新規導入ではなく、**使い方を決める**話。

### 6.2 比較

| 観点 | Gemini 3.1 Flash Image（既定） | Gemini 3 Pro Image | OpenAI gpt-image-2 | Imagen 4 | **生成しない**（SVG/HTML合成） |
|---|---|---|---|---|---|
| 連携のしやすさ | **導入済み**。鍵も画面にある | 同上（モデル名の変更のみ） | 新しい鍵・新しい実装が必要 | 同系。実装追加 | **既存**（`figures.mjs`/`board.mjs`/`saveimage.mjs`） |
| 日本語の文字 | 弱い。崩れる | ややまし。だが保証はない | 比較記事では日本語入り画像に優位との報告 | 弱い | **完全に正確**（文字はフォントで描く） |
| 教材への適性 | 挿絵・背景は良好 | 同上 | 同上 | 同上 | 図・板書・表に最適 |
| 修正・再生成 | 容易（プロンプト修正） | 容易 | 容易 | 容易 | **決定的**。同じ入力＝同じ出力 |

| 児童向けの安全性 | 安全フィルタあり＋こちらの指示で抑制 | 同上 | 同上 | 同上 | **最も安全** |

| 保存 | base64 → 案件フォルダへPNG保存 | 同上 | 同上 | 同上 | SVG＋ブラウザでPNG化（実装済み） |

出典: [Gemini API 料金の解説（2026年8月）](https://developer.puter.com/tutorials/gemini-api-pricing/) ／
[Gemini 画像生成 API 価格](https://www.aifreeapi.com/en/posts/gemini-image-generation-api-pricing) ／

### 6.3 結論と代替経路

**推奨: Gemini を第一候補として続ける。ただし日本語の文字は画像生成に描かせない。**

```
文字あり掲示物 ＝ 画像生成（背景・挿絵、文字なし）
                ＋ SVG/HTML（文字・レイアウト。フォントで正確に描く）
                ＋ ブラウザで1枚のPNGに合成（saveimage.mjs の仕組みを拡張）
```

この方式なら、日本語が崩れる問題は**原理的に起きない**。
そして必要な部品（SVG描画・印刷用HTML・SVG→PNG変換）は**すでにこのリポジトリにある**。

**代替経路（止めないための備え）**:

1. 画像APIが失敗・未設定 → 挿絵を**枠だけのプレースホルダ**にして、文字とレイアウトは完成させる。
   工程は `done` にし、「挿絵は未生成」を未確定事項に記録。**ワークフローは止めない**
2. 予算上限に達した → 同上（プレースホルダ）
3. どうしても写実的な絵が要る → CEO に「手持ちの写真を入れてください」と依頼（参照画像として投入可能）
4. 将来 gpt-image-2 等を足す場合は `ImageProvider` インタフェースを切って差し替え式にする

### 7.1 比較

| | ①Googleドライブ同期＋参照フォルダ | ②ブリッジの索引（キーワード＋見出し） | ③ローカル埋め込み検索（RAG） | ④クラウドのベクトルDB |

### 7.2 推奨構成（段階式）

**段階1（すぐ・追加実装ゼロ）**
Google ドライブ（デスクトップ版）で同期したフォルダを、**既存の `--ref` 参照フォルダとして読む**。

```
起動.bat の REFPATH に:
  指導要領=C:\Users\...\Google ドライブ\マイドライブ\教育資料\指導要領
  実践事例=C:\Users\...\Google ドライブ\マイドライブ\教育資料\実践事例
```

ドライブAPIの連携も認証も要らない。同期フォルダはただのローカルフォルダなので、
**すでに動いている読み取り専用の仕組みがそのまま使える。**
学習指導要領・解説は、文部科学省のサイトから取得してここに置く。

> 文部科学省ウェブサイトの内容は政府標準利用規約（第2.0版）に沿い、出典表示のうえ
> 複製・翻案が認められる（CC BY 4.0 互換）。ただし**大量印刷・出版等の二次利用は
> 別途相談が必要**とされているため、**学級での利用のためにPC内へ保存して参照する範囲**に留める。
> 出典: [文部科学省ウェブサイト利用規約](https://www.mext.go.jp/b_menu/1351168.htm)

**段階2（資料が増えたら）**
ブリッジに索引を作る。各資料の先頭の見出し・分類タグ・学年・教科を抽出して
`索引.json` に持ち、検索前に候補を絞る。**決定的な処理**なので壊れても直せる。

**段階3（必要になったら）**
埋め込みによる意味検索。ローカルに `index.sqlite`。ただし——

**なぜ段階3を今やらないか**: CEO は開発者ではなく、更新は `更新.bat` のダブルクリックで行っている。
埋め込みモデルをローカルに入れる（数百MBのダウンロードと実行環境）か、
埋め込みAPIを毎回叩く（費用と通信）かの二択になり、どちらも今の運用の手軽さを壊す。
**資料が数百ファイルを超え、キーワード検索で目的の資料に辿り着けなくなってから**着手する。

## 8. 書庫（知識と記憶）

### 8.1 保存するもの / 保存しないもの

`bridge/memory.mjs` を構造化して拡張する。

```
99_書庫/
  好み.md          指導上の重視点、よく使う表現、好みの文章構成・デザイン
  判断履歴.md      採用した提案／却下した提案とその理由
  傾向.md          学級全体の一般的傾向、つまずきの傾向、効果があった支援
  振り返り.md      授業後の振り返り、授業改善の記録
  型/              再利用できるテンプレート・素材
  過去案件/        完了した案件（依頼票・構成案・成果物）
  索引.json        検索用
```

**保存しない**（要件・追加4）: 児童の氏名／出席番号／顔写真／個人を識別できる音声・映像／
住所・連絡先／成績や診断など特定の児童と結びつく情報／**組み合わせると個人が推測できる記録**。

### 8.2 個人情報の検査（保存前）

**二段構え。決定的な検査を先に、LLM の判断を後に。**

1. **決定的な検査**（ブリッジ側・新規 `bridge/pii.mjs`）
   - 電話番号・郵便番号・生年月日・メールアドレス・住所らしい文字列の正規表現
   - 「◯年◯組」＋数字の組み合わせ、出席番号らしい表記
   - 匿名IDの規則（`[A-Z]児`）**以外**の人名らしい語（姓名の辞書ではなく、
     「さん」「くん」「ちゃん」に前接する2〜4文字など、書式で拾う）
   - 該当したら**保存を止め、該当箇所を示して警告する**
2. **個人情報ガード（エージェント）** が、1で拾った候補だけを見て、匿名化するか削除するかを決める
3. 迷ったら**保存しない**（既定を安全側に倒す）

決定的な検査を先に置くのは、LLM は見落とすことがあるが正規表現は見落とさないため。
逆に正規表現は取りすぎるので、そこだけ LLM に判断させる。

### 8.3 更新・検索・保存期間・削除

| 項目 | 設計 |
|---|---|
| 更新 | 案件完了時に記録担当が追記。同じ趣旨の記録は増やさない（既存 `memory.mjs` の重複排除を流用） |
| 検索 | 依頼票の教科・学年・単元名で索引を引き、該当分だけをプロンプトに載せる（全部は載せない） |
| 保存期間 | 好み・型は無期限。傾向・振り返りは**年度末に見直しを促す**（自動削除はしない） |
| 上限 | 各ファイル100件。超えたら古いものから落とす（既存の仕組みと同じ） |
| 削除 | 書庫はただのMarkdownなので**エクスプローラで開いて消せる**。加えてアプリから「この記録を削除」ができるようにする |
| 監査 | 何をいつ保存したかを `書庫/履歴.md` に残す |

## 11. 想定される問題と対策

| 問題 | なぜ起きるか | 対策 |
|---|---|---|
| **費用の膨張** | 部門が13、エージェントが50体を超える | ①サブは全部 Haiku ②段取りに載った部門しか動かない ③承認待ち①で**見積り金額を表示** ④案件ごとの上限額を設定し、超えたら停止して CEO に確認 |
| **待ち時間が長い** | 工程が増えた | ①並列グループを最大化 ②フロア図で進捗を可視化 ③構成案の段階で「ここまで約◯分」を出す |
| **秘書室が詰まる** | 全部が秘書長を通る | 秘書長は方針だけ。進捗管理と統合を別担当に分けてある（§4.1） |
| **差し戻しの無限ループ** | 品質基準に永久に届かない | 3回でCEOにエスカレーション（§3.4） |
| **LLMが工程を飛ばす** | 司会をLLMにすると起きる | **制御層を決定的なコードにする**（§3.1） |
| **品質管理室が自分を承認** | 監査の独立性が崩れる | 別部屋・判定と進路の分離・記録の保存・再検査必須（§4.8） |
| **プロンプトが長くなりすぎる** | 依頼票＋単元＋書庫＋資料を全部載せると溢れる | 依頼票は600字以内に要約。資料は索引で絞って必要分だけ。書庫は該当分だけ |
| **個人情報の混入** | CEO が実名を打ってしまう | 保存前の決定的検査＋警告（§8.2）。成果物側は既存 S1 が匿名IDに置換 |
| **既存の使い方が壊れる** | 大改造のため | 単元を作らない直接依頼を残す（§9）。既存部門の定義は変えない（単元設計室を除く） |
| **画像生成が使えない** | API・予算・規約 | 代替経路（§6.3）。工程は止めない |
| **一度に作りすぎて確認できない** | 成果物が大量に出る | 承認待ち②で一覧＋差分を出す。品質管理の指摘一覧も添える |

## 12. CEO に確認したいこと

   「CEO（担任）」とするか。**推奨: CEO（担任）**
