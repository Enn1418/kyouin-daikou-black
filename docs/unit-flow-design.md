# 単元を背骨にする — 部屋どうしの連携

担任の指摘（2026-08-23）:

> 各部屋がつながっていないと、結果的に独立したものができるだけで、単元全体を通した学習設計ができない。
> 単元設計室で計画を立てても、実際に問いを作ったり板書を考えたりする全体の流れができないと、
> 各部屋に最初から構想を伝えないといけないので、非常に手間がかかる。**いまのままでは全く使えません。**

---

## 1. なぜつながらないのか

**アプリの中に「単元」という存在がない。仕事の単位が「部屋」になっている。**

```ts
// いまの構造（部屋ごと）
RoomState { userBrief, tasks, agentHistories, finalOutput, ... }
```

部屋は自分の `userBrief`（担任が口で伝えた依頼文）しか知らない。
単元は部屋をまたぐのに、それを表す入れ物がどこにもない。
だから板書室に入るたび、算数教材室に入るたび、担任が構想を口で伝え直すことになる。

同時実行（2026-08-23 実装）で「部屋が並行して動く」ようにはなったが、
**並行して動く部屋どうしが同じ単元を見ていない。** 独立した成果物が増えるだけになっている。

## 2. 直し方 — 三層

### 第1層: 単元を第一級の入れ物にする（背骨）

```ts
interface Unit {
  id: string;
  name: string;              // 「かさ（LとdL）」
  subject: string;           // 算数
  hours: number;             // 全6時間
  participants: string[];    // ['A児','B児','D児'] 匿名IDのみ。氏名は入らない
  goal: string;              // 単元のゴール（担任承認済み）
  hourGoals: { hour: number; goal: string }[];
  wording: { medate?: string; matome?: string };  // 全部屋で揃える言い回し
  approvedAt: string | null; // 担任がゴールを承認した日時
  folder: string;            // 04_単元/かさ_2026-09/
  deliverables: Deliverable[];
  handoffs: Handoff[];
  status: '設計中' | '進行中' | '完了';
}

interface Handoff {          // 部屋から部屋への発注
  id: string; unitId: string;
  fromRoomId: string; toRoomId: string;
  title: string; brief: string; hour?: number;
  status: '承認待ち' | '待機中' | '実行中' | '完了' | '見送り';
}

interface Deliverable { roomId: string; title: string; path?: string; hour?: number; at: string; }
```

新しい `unitStore`（永続化）。ブリッジ接続時は `04_単元/<単元名>/単元シート.md` にも書き出す
（担任が直接編集できる／アプリを閉じても残る）。**アプリ内にも持つので、ブリッジ未接続でも動く。**

### 第2層: 全部屋が単元を最初から知っている（再説明が消える）

`PromptBuilder` に S14 を追加。`teamType === '特別支援'` の全部屋のシステムプロンプト先頭に、
いま選ばれている単元の**短い**ヘッダーを差し込む（毎回のプロンプトに載るので長くしない）:

```
【いま作っている単元】かさ（LとdL）／算数／全6時間／参加: A児・B児・D児
単元のゴール: …（担任承認済み 2026-08-23）
各時間のゴール: 1) … 2) … 3) …
揃える言い回し: めあて「…」／まとめ「…」
詳しくは 04_単元/かさ_2026-09/単元シート.md（read_file で読める）
```

**これだけで「毎回構想を伝え直す」手間は消える。**
板書室に入って「3時間目の板書」と言えば通じる。

### 第3層: 部屋から部屋へ発注できる（流れができる）

リードエージェント用の新ツール:

- `propose_unit(...)` — 単元設計室のリードが単元案を出す（担任の承認で確定）
- `request_room(toRoomId, title, brief, hour?)` — 他の部屋への発注。**承認待ちで止まる**
- `register_deliverable(title, path, hour)` — 完成物を単元に登録（`deliver_project` から自動でも呼ぶ）

承認されたら `roomManager.ensure(toRoomId)` → `startProject(brief, toRoomId)` で相手の部屋が動き出す。
**同時実行はすでに出来ているので、複数の部屋が並行して進む。**
発注先が作業中なら `待機中` に置き、空いたら自動で始める（取りこぼさないため）。

## 3. 承認ゲートは2つだけ

| ゲート | 何を承認するか | なぜ止めるか |
|---|---|---|
| **① 単元のゴール** | 単元・各時間のゴール、参加児童 | ここがずれたまま5部屋が動くと**全部やり直し**になる |
| **② 段取り** | どの部屋に何を頼むか（一覧・チェックを外せる） | 費用と暴走の歯止め。担任のAPIキーで動くので全自動は危ない |

それ以外では止めない。ゲート②は「まとめて1回」。部屋ごとに5回聞かれるのは、いまと同じ手間になる。

## 4. 単元フォルダ

いまは `01_教材/算数` に散る。単元ごとに集める:

```
04_単元/かさ_2026-09/
  単元シート.md          ← 背骨。担任も編集できる
  01_板書/1時間目.md
  02_教材/3時間目_基礎.md  標準.md  発展.md
  03_絵カード/
  04_おたより/
```

既存の `01_教材/` は残す（単元に属さない単発の教材はこれまでどおり）。

## 5. 画面

- **ヘッダー**: 「いま作っている単元」のバー（切替・新規作成）。全画面で共通
- **フロア図**: その単元を担当している部屋を濃く、していない部屋を薄く。
  部屋の下に「この単元での役割（例: 3時間目の板書）」を出す
- **単元ビュー（新）**: 流れ図（設計→承認→各部屋→仕上げ）と、時間ごとの成果物の表。
  承認待ちの発注はここに並ぶ

## 6. 段階

| 段階 | 内容 | 効果 |
|---|---|---|
| **P1** | `unitStore` ＋ S14 の注入 ＋ ヘッダーのバー | **再説明の手間が消える**（ここが最重要） |
| **P2** | `request_room` ＋ 承認UI ＋ 発注の記録 | 部屋から部屋へ流れる |
| **P3** | 単元ビュー（流れ図・成果物表）＋ 単元フォルダへの集約 | どこで何が行われているか1枚で見える |
| **P4** | 完了の戻り（発注元への通知）・単元シートの自動更新 | 単元シートが常に最新になる |

P1 だけでも実用になる。P2 以降は「手間が減る」度合いの話。

## 7. 担任に決めてもらうこと

1. **承認の粒度** — 段取りをまとめて1回か、部屋ごとに1つずつか
   → 推奨: **まとめて1回**（一覧でチェックを外せる）
2. **単元を同時に何本持つか** — 1本だけか、複数か
   → 推奨: **複数持てるが「いま作っている単元」は1つ選ぶ**
3. **単元設計室が司令塔でよいか** — 他の部屋（板書室など）からも発注できるようにするか
   → 推奨: **司令塔は単元設計室。ただし板書室→視覚教材室のような近い部屋どうしの発注は許す**
4. **既存の単発の使い方を残すか** — 単元に属さない「今日の1枚」も従来どおり作れるようにするか
   → 推奨: **残す**（単元を選んでいなければ、いままでと同じ動き）
