# 特別支援学級 保護者向け「その日の手紙」ワークフロー構築プラン

作成日: 2026-08-11 / 対象: 特別支援学級担任（1学級・数名〜十数名想定）

---

## 0. まず結論

**AIで手紙を書くこと自体は、この仕組みの一番簡単な部分です。**
本当のボトルネックは次の2つで、プランはここを軸に組みます。

| 困りごと | 本当の原因 | このプランでの解 |
|---|---|---|
| 時間がなくて書けない | 白紙から文章を作る作業が重い | 生ログ → AI下書き → 教員が確認だけ、に変える |
| その場で記録できず忘れる | メモを取る動作が「立ち止まる」ことを要求する | 歩きながら10秒で吹き込む。整形は後でAIがやる |

そして**最初にプリンターを買わないこと**。Phase 0（道具ゼロ・1週間）で「毎日記録が溜まるか」を先に検証します。記録が溜まらなければ、プリンターがあっても印刷するものがありません。

---

## 1. 全体像

```
 ①捕捉        ②集積          ③構造化        ④生成         ⑤確認      ⑥印刷
 ボイス      その日の        児童ごとに      手紙文に      教員が      50mm感熱紙
 レコーダー → フォルダに   → 自動で分割   → リライト   → 目視・   → に印刷
 / テキスト   生ログ蓄積      + タグ付け     (120〜200字)   修正       + PDF保存
   (10秒)      (自動)         (Claude)      (Claude)      (1〜2分)    (ボタン1つ)
```

1日の教員の作業量の目標は **その場10秒 × 数回 ＋ 放課後5分**。これを超えたら仕組みが失敗しているサインです。

## 2. 各工程の設計

### ① 捕捉 ― 「その場で10秒」に落とす

**吹き込みテンプレート（これだけ守る）**

> 「**〇〇さん**、**給食**で、**自分からおかわりって言えた**」
> 　└名前　　　└場面　　　└できごと

名前を**必ず最初**に言うのが肝です。後工程の児童別振り分けが機械的に処理できます。場面（朝の会／国語／休み時間／給食／掃除／帰りの会）も言えると、手紙に情景が出ます。

**捕捉の3ルート（併用可）**

- **A. Plaud NotePin S**：胸元・襟元に装着し、タップで録音開始。アプリが自動で文字起こし。両手が塞がる場面が多い特支の現場と相性が良いのが最大の利点です。
- **B. スマホの音声入力**：手持ちの端末で十分。コスト0で今日から始められる。Phase 0はこれで回します。
- **C. テキスト直接入力**：落ち着いた時間帯や、放課後の振り返り用。

**忘れ防止の運用**
- 帰りの会の後に**5分の「まとめ吹き込みタイム」**を固定化。その日の抜けをここで拾う。
- 週末に「今週まだ手紙が少ない子」をAIに出させる（→ 7章）。毎日全員は物理的に無理なので、**「1週間に最低2通」を保証する**運用に切り替えるのが現実的です。

### ② 集積 ― その日のフォルダ

```
renraku/
├── roster.private.csv          # 児童ID ⇔ 実名 の対応表（Git管理外・要暗号化）
├── records/
│   └── 2026-08-11/             ← 「その日のフォルダ」
│       ├── 00_raw.md           # 吹き込み・入力の生ログ（時刻つきで追記）
│       ├── 10_split.json       # 児童ごとに分割・構造化した結果
│       ├── letters/
│       │   ├── A01.md          # 手紙の下書き（AI生成）
│       │   └── A03.md
│       └── print/
│           ├── A01.png         # 印刷用画像（幅384px）
│           └── A03.png
├── children/
│   └── A01/history.md          # その子の記録の通し履歴（学期末に効いてくる）
├── tools/
│   ├── render_letter.py        # md → 384px 画像
│   └── print_letter.py         # 画像 → プリンター
└── .claude/
    └── skills/letter/SKILL.md  # 手紙の文体ルール（AIへの指示書）
```

`00_raw.md` の実際の中身:

```markdown
# 2026-08-11 (火)

- 09:20 たろうさん、朝の会で、日直の号令を自分から言えた。声も大きかった
- 10:45 はなこさん、算数、繰り上がりで手が止まって不安そう。ヒント出したら最後までやりきった
- 12:30 たろうさん、給食で自分からおかわりって言えた
- 15:10 じろうさん、掃除でほうきの担当を最後まで。終わりの合図まで続けられた
```

### ③④ 構造化と生成 ― Claude Code に任せる

Pythonのパイプラインを自作しない、というのが本プランの重要な判断です。「生ログを読んで、児童ごとに分けて、手紙にして、ファイルに保存する」——これは**Claude Code がファイル操作としてそのまま実行できる仕事**です。自作スクリプトを増やすほど、壊れたときに直せる人が担任1人だけになります。

放課後にやることは、実質これだけ:

```
$ claude
> 今日の記録から手紙を作って
```

そのために `.claude/skills/letter/SKILL.md` に**文体ルールを一度だけ書いておきます**（→ 6章）。以降、AIは毎回そのルールに従います。

### ⑤ 確認 ― ここは絶対に省かない

**AIの出力をそのまま保護者に渡さない。** 理由は2つ。

1. **記録にないことを書いてしまう危険**（ハルシネーション）。「楽しそうでした」程度でも、事実でなければ保護者との信頼を損ないます。
2. 保護者への文書は最終的に教員の責任で出すものです。

対策として、手紙ファイルには**必ず根拠ログを併記**させます:

```markdown
<!-- 根拠: 09:20 朝の会 日直の号令を自分から / 12:30 給食 自分からおかわり -->

たろうさん、今日は朝の会で日直の号令を自分から言うことができました。
声もはっきりしていて、みんなに届いていました。給食では「おかわり」と
自分から言えた場面もありました。ご家庭でも聞いてみてください。
```

コメント部分は印刷されません。教員は**根拠と本文を突き合わせるだけ**で確認が済みます。1通15秒、5通で1分半。

### ⑥ 印刷 ― 50mm感熱紙

**推奨は「印字幅48mm / 384ドット」クラス。** 「50ミリ程度」の実売品はほぼこの規格に収まり、以下のどちらでも同じ384px画像を流用できます。

| 候補 | 特徴 | 向き |
|---|---|---|
| **Phomemo M02 系**（53mm紙 / 384dot） | バッテリー内蔵・BLE・**シール紙が使える** | ◎ 連絡帳に貼れる。教室で持ち歩ける |
| **58mm ESC/POSレシートプリンタ**（印字48mm / 384dot） | 安価・入手性抜群・USB/BT | ○ 職員室据え置き向き |
| Epson TM 系 | 業務用の安定性 | △ 価格が跳ねる |

**技術的な要点：日本語はテキストとして送らず、画像にして送る。**
ESC/POS のテキストモードは日本語（特に機種依存のコードページ）で文字化けしやすく、ここで詰まる事例が多い工程です。Pillow で Noto Sans JP を使って **幅384pxの画像をレンダリングし、ラスター画像として印刷**すれば、フォントも改行も完全に制御できます。これは実績のある定番手法です。

**文字数の制約（生成側にも効く）**
384ドット幅では、実用的な可読サイズ（24〜26px）で **全角12〜14文字/行**。手紙1通を **120〜200字** に収める設計にします。これは⑥の都合であると同時に、**保護者が毎日無理なく読める長さ**でもあり、教員の確認時間も短く保てます。制約がそのまま品質になる、という良い例です。

**感熱紙の弱点は運用でカバーする**
感熱紙の印字は保存環境しだいで**数か月〜数年で退色**します。記念に取っておきたい保護者にはこれは不利です。

- 手紙は「その日の速報」と位置づけ、**シール紙で連絡帳に貼る**運用にする
- 原本は必ず**PDF/テキストで手元に保存**（`records/` にすでに残っている）
- 学期末に「〇〇さんの1学期」としてまとめ、**普通紙で1枚**にして渡す ← 保護者の満足度はこちらの方が高い可能性があります

## 3. 個人情報の扱い ― 着手前に確認すべきこと

**このプランで最も慎重を要する部分です。技術的にどう作るかより先に、勤務校・教育委員会の規程を確認してください。**

確認すべき3点:

1. **生成AIの校務利用**が認められているか（自治体ごとにガイドラインの有無・範囲が異なります）
2. **児童の情報をクラウドサービスに送信**してよいか、どの範囲までか
3. **校務PC**でのソフトウェア導入・外部機器接続の可否

### 設計側での軽減策

**実名をクラウドに出さない二層構造にします。**

```
roster.private.csv（ローカルのみ・Git管理外）
  A01,山田 たろう
  A02,佐藤 はなこ

記録・AI処理は全て「A01」で行う
  ↓
印刷の直前に、ローカルで A01 → 「たろうさん」に置換
```

これで**氏名はAIにも外部にも渡りません**。ただし本文の記述内容自体から個人が推測されうる点は残るため、規程確認の代替にはなりません。

### その他の必須事項

- **Gitには絶対にコミットしない。** private リポジトリでも避けてください。`.gitignore` に `records/`, `children/`, `*.private.*` を入れ、保管はローカル＋暗号化バックアップ（校務規程に沿った方法）で。
- **Plaud はクラウドで文字起こしします**（音声が事業者サーバに送られます）。ここが規程上の最大の論点になり得ます。**完全ローカルで処理したい場合の代替**として、スマホで録音 → PC上の `whisper.cpp` / `faster-whisper` で文字起こし、という構成があります。精度は実用十分で、音声が外に出ません。判断が難しければ**Phase 1 はこちらから始める**のが安全です。
- 保護者への周知（AIで下書きを作成し教員が確認して発行している旨）も、トラブル予防として検討の価値があります。

## 6. 手紙の文体ルール（`.claude/skills/letter/SKILL.md` のたたき台）

```markdown
# 保護者向け連絡手紙の作成ルール

## 目的
その日の記録から、保護者が読んで安心し、家庭での会話のきっかけになる短い手紙を作る。

## 構成（3文）
1. 事実 ― いつ・どの場面で・何ができたか（記録にある事実のみ）
2. 様子 ― そのときの表情・声・取り組みの様子
3. 家庭へのひとこと ― 話題にしやすい問いかけ、または一言のねぎらい

## 分量
120〜200字。感熱紙50mm幅（全角12〜14文字/行）で印刷するため厳守。

## 呼称
「〇〇さん」で統一。

## 書くこと
- できたこと、挑戦したこと、続けられたこと
- 小さな変化（昨日より1分長く座れた、など）

## 書かないこと
- 記録にない推測（「楽しそうでした」も記録になければ書かない）
- 診断名・障害特性に関する断定的な記述
- 他の児童との比較、順位、評価的な言い回し
- 課題を課題のまま終える文（「〜に挑戦中です」「〜を一緒に練習しています」と前向きな現在進行形にする）

## 出力形式
ファイル冒頭に根拠ログをHTMLコメントで併記する（印刷されない）。
<!-- 根拠: 09:20 朝の会 日直の号令 / 12:30 給食 おかわり -->

## 手順
1. records/<日付>/00_raw.md を読む
2. 児童ID（roster.private.csv で照合）ごとに記録を分割し 10_split.json に保存
3. 児童ごとに手紙を letters/<児童ID>.md に生成
4. children/<児童ID>/history.md に今日の記録を追記
5. 記録が1件もない児童は手紙を作らない（作文しない）
```

**最後の1行が重要です。** 記録がない子の手紙をAIに作らせないでください。全員分揃えたい気持ちは自然ですが、そこで生まれるのは事実に基づかない文章です。「今日は手紙がない」という情報のほうが、翌日の観察の指針として価値があります。

## 7. 週次チェック（Phase 3）

```
> 今週、手紙が2通未満の子を教えて
```

```
A03 じろうさん  0通  ← 最終記録 8/4
A05 さくらさん  1通
```

手が掛かる子ほど記録が増え、落ち着いている子ほど記録が減る——という偏りは意識していても起きます。ここを機械に見張らせるのは、この仕組みの隠れた本命です。

## 8. うまくいかないときの判断基準

| 症状 | 対処 |
|---|---|
| 吹き込みを忘れる | 場面を1つに固定（給食の時だけ、など）。全場面を狙わない |
| 1日10分を超える | 手紙の宛先を「毎日全員」から「1日3名ローテーション」に変更 |
| 文体が自分と違う | SKILL.md に自分の過去の手紙を3通貼る。AIはそれを真似ます |
| AIが事実でないことを書く | 根拠コメントを必ず確認。記録の粒度が粗い可能性 |
| 印字が薄い・ずれる | フォントサイズと余白の調整。感熱紙の裏表も確認 |

**撤退の目安**: Phase 0 の1週間で記録が溜まらなかった場合、機材を買う前に立ち止まってください。原因はワークフローではなく、記録を取るタイミングの設計にあります。

## 付録A: 印刷スクリプトの骨格

`tools/render_letter.py` ― Markdown を 384px 幅の画像に

```python
from PIL import Image, ImageDraw, ImageFont
import re, sys, textwrap

WIDTH = 384                    # 印字幅48mm = 384ドット
FONT  = "/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc"
SIZE  = 26                     # 実物を見て調整する
PER_LINE = 13                  # 全角の1行文字数

def render(md_path, out_path, name, date):
    body = open(md_path, encoding="utf-8").read()
    body = re.sub(r"<!--.*?-->", "", body, flags=re.S).strip()   # 根拠コメントを除去

    font  = ImageFont.truetype(FONT, SIZE)
    small = ImageFont.truetype(FONT, 18)
    lines = [l for p in body.split("\n") for l in textwrap.wrap(p, PER_LINE) or [""]]

    h = 40 + 30 + len(lines) * (SIZE + 10) + 40
    img = Image.new("1", (WIDTH, h), 1)          # 1bit白黒
    d = ImageDraw.Draw(img)

    d.text((10, 12), f"{date}  {name}", font=small, fill=0)
    d.line((10, 42, WIDTH - 10, 42), fill=0)
    y = 58
    for l in lines:
        d.text((10, y), l, font=font, fill=0)
        y += SIZE + 10

    img.save(out_path)

if __name__ == "__main__":
    render(*sys.argv[1:5])
```

`tools/print_letter.py` ― 画像をプリンターへ（58mm ESC/POS の場合）

```python
from escpos.printer import Usb, Serial   # pip install python-escpos
import sys

# USB接続の例。ベンダーID/プロダクトIDは `lsusb` で確認
p = Usb(0x0416, 0x5011)
p.image(sys.argv[1])
p.cut()      # カッター非搭載機では p.control("LF") を数回
```

Phomemo M02系（BLE）を使う場合は `python-escpos` ではなく、BLEで画像を送るOSSライブラリ（`phomemo-tools` / `phomemo_m02s` など）が利用できます。いずれも**384px幅の画像を渡す**という点は共通なので、`render_letter.py` はそのまま使い回せます。
