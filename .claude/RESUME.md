## 実地確認で分かったこと（2026-08-22・担任の Windows PC で初回起動）

起動・4体のアバター・チーム選択までは問題なし。詰まったのは全部この周辺だった。

- **ブリッジの接続状態を localStorage に残していなかった** ので、再読み込みのたびに
  未接続へ戻り、ファイル系ツールが黙って消えていた。→ 起動時に自動で繋ぎ直す（`autoConnectBridge`）
- **トークンを起動のたびに作り直していた** ので、ブリッジを再起動すると設定が無効になっていた。
  → 教材フォルダ直下の `.bridge-token` に保存して使い回す（ドット始まりなので一覧にも出ず、
  拡張子ホワイトリストにも当たらないのでブリッジ越しには読めない）
- **接続状態が画面のどこにも出ていなかった。** → ヘッダーにフォルダのアイコン（緑/灰/赤）
- **URL とトークンが横並びの無ラベル入力**で、トークン欄が見つけられなかった。
  → 縦積み＋①②の見出し。押せない理由もその場に書く
- **ブラウザの自動翻訳で画面が真っ白になった。** `lang="en"` のままだったので Chrome が翻訳を提案し、
  翻訳がテキストノードを差し替えた直後に React が落ちていた。
  → `lang="ja" translate="no"` ＋ notranslate、加えて `ErrorBoundary` で白画面を避ける
- プロンプト S8 を具体化（`00_共通/学級の実態.md` を最初に読む）。
  未接続時は「教材フォルダを接続すると実態を読める」と言い添えるようにした

**まだ確認できていないのは出力の質そのもの**（3段階の差・分量・保存先）。ここが次の焦点。

## 実地確認3回目（2026-08-22）— 実態は読めていた。指示の側が間違っていた

担任の実際の `学級の実態.md` は **A児〜G児の7名（1〜4年）**。エージェントは確かに読んでいた
（A児1年・B児2年は記述どおり）。にもかかわらず3人分しか作らなかったのは、
**こちらが渡した依頼文が「A児・B児・C児の3段階で」だったから**。
架空の3人組の雛形をなぞった文面を手順書に載せていた。

- リードの手順を修正：人数は実態記述のとおり。3人と決めつけない。**全員をどれかの段階に割り振る**
  （1段階に複数人でよい）。担任が絞ったときだけその児童に限る。誰も取りこぼさない。
  各プリントの先頭に「対象: ○児・○児」を書く
- 学級全体の欄（集中15分・1枚に収める・使用教材）を時間配分と分量に反映させる
- プロンプト S12 を追加（全特支チーム共通）：人数を勝手に減らさない・対象児童を明記
- 手順書の依頼文例を「学級全員を3段階に分けて」に差し替え。児童IDを並べる必要はない
- サブエージェントの指示を図ブロック前提に更新（`[レイアウト]` は写真など描けないものだけ）

**教訓**: 雛形にも手順書にも架空の具体例を書くと、それが仕様として流れ込む。
例示は「形」だけにして、中身は担任のファイルから来るようにする。

## 完了済み（参照フォルダ・2026-08-22）

- **Obsidian は繋がる**。保管庫はただの Markdown フォルダなので、読めるようにするだけでよかった

  名前がぶつかったら番号を足す（黙って別フォルダを読ませない）。パス脱出は従来どおり遮断
- `bridge/search.mjs` + `GET /search` — 保管庫は数千ファイルになるので一覧は成り立たない。
  語で探して当たった前後だけ返す。複数語は AND。隠しフォルダは見ない。512KB/4000ファイルで打ち切り
- ツール `search_files`、`list_files` / `read_file` に `root`。**参照フォルダがあるときだけ**載る

## 完了済み（2026-08-24・続）— 秘書室が案件を作れなかった不具合

CEO の実地確認: 秘書室に依頼を伝えても、案件を作る手段がなく行き止まりだった（③）。
続けて発生した2つ目の不具合: 案件は作れても、会話が「実態確認します」で止まって見えた。

- **1つ目の直し**: `create_job` / `update_requirement_sheet` / `lock_requirement_sheet`
  （`src/core/agent/tools/jobTools.ts`）。秘書室の窓口（`sec-chief`・`sec-intake`）だけが使える。
  idle でも working でも渡す（CEO は最初のひとことで依頼するため）。
  推測で埋めない規約はツールの説明文に書く（モデルが実際に読む場所）
- **2つ目の直し（本質的な原因）**: 部屋の心拍（`AgentSimulation` の定期実行）は
  `phase === 'working'` のときしか回らない。`create_job` は部屋を idle のまま案件だけ作っていたので、
  最初の受け答えのあと誰も次の一手を打たず、会話が止まって見えていた。
  `create_job` の時点で `startProject()` を呼んで部屋を働かせるよう修正（idle のときだけ。
  すでに working なら上書きしない）
- 権限（誰が何をできるか）を `src/core/agent/permissions.ts` に集約し、直接テストできるようにした

**続報（2026-08-24）**: 上記だけでは足りず、CEO の実地確認で「秘書室は進むが、その先（単元設計室）が
動き出さない」ことが判明。根本原因はエンジン側の隠れた挙動だった。

- `AgentSimulation.checkProjectCompletion()` → `AgentBrain.concludeProject()` が、
  **部屋の内部タスクが全部終わると、リードに「deliver_project を使え」と固定文面で促す仕組み**
  （通常の制作部屋を前提にしたもの）
- 秘書室・品質管理室のリードにも `deliver_project` を渡していたため、リードはその指示に従い、
  本来呼ぶべき `set_work_plan`／`submit_qa_verdict` ではなく `deliver_project` を呼んでしまい、
  **その部屋の phase が 'done' になって心拍が止まった**（心拍は working のときしか回らない）。
  単元設計室への段取り登録が一度も起きなかったのは、これが直接の原因
- 直し: `permissions.ts` に `ORCHESTRATION_LEADS`（sec-chief・qa-chief）を追加。
  ①`ToolRegistry` がこの2人には `deliver_project` を渡さない
  ②`AgentBrain.concludeProject()` が、この2人には部屋に合った文面（段取りの状態を確認する／
  検査結果をまとめて判定する）を送るよう分岐
- 併せて `set_work_plan` に、承認待ち①以降の案件へ段取りを重ねて登録できないようにする
  安全弁を追加（二重呼び出しで承認済み・進行中の工程が黙って消える事故を防ぐ）
